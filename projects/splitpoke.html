SplitPoke

A real-world multiplayer expense splitter built as an agentic MCP server: friends can create groups, record expenses, see fair balances, and settle up through a conversational interface.

TypeScriptModel Context ProtocolHTTP / SSESQLiteRailwayPoke Recipes

Agentic MCP architecture

SplitPoke exposes focused tools—create_group, join_group, add_expense, get_balances, list_expenses, and settle_up—through a Model Context Protocol server over HTTP/SSE. The agent can select the right operation from natural language while the server remains responsible for validation, persistence, and deterministic financial behavior.

This is the important boundary: the model handles intent; the service handles money and state.

Money that cannot drift

Every amount is stored as an integer number of cents. Equal splits distribute any remainder deterministically instead of allowing JavaScript floating-point arithmetic to introduce silent precision errors.

That design makes balances reproducible, auditable, and safe for the everyday edge cases that make shared-expense products frustrating.

Multilateral debt netting

Balances are computed across the group, then simplified into a smaller set of payments. The settlement engine treats the group as a debt graph: credits and debits are netted, and a greedy transfer strategy matches people who owe with people who should receive.

EXPENSES → MEMBER BALANCES → NETTED DEBT GRAPH → FEWER SETTLEMENT PAYMENTS

The result is not merely “who owes what.” It is a practical settle-up plan that reduces payment friction for the whole group.

Identity and durable state

Identity comes from the X-Poke-User-Id header supplied by Poke, so the server does not need to invent a second login flow. Groups, memberships, expenses, and balances persist in SQLite, with a data layer that can move to Postgres when scale requires it.

State is scoped to the authenticated user and validated at the tool boundary, keeping conversational convenience from becoming data ambiguity.

Containerized delivery

The service is designed to run as a small production container with a persistent database volume. Railway deployment uses a predictable build/start path and a /healthz endpoint for platform health checks.

  • Node 22.5+ built-in SQLite support avoids native dependency overhead.
  • Environment-based configuration separates local development from production.
  • Bearer authentication can protect the MCP endpoint.

Product loop, not just an API

The onboarding flow is designed around a real social moment: create a group for a trip, receive a join code, and invite friends. A shareable Poke Recipe gives the group an easy entry point, creating a viral loop where every useful expense group can bring in additional users.

This combines product thinking with systems engineering: lower onboarding friction, clear confirmation of amounts and group codes, and a path from a personal tool to a repeatable shared workflow.

Why it matters as a technical-lead case study

SplitPoke demonstrates the decisions that make an AI-enabled product trustworthy: strict domain boundaries, deterministic arithmetic, explicit identity propagation, durable state, deployability, health observability, and a user journey that explains why the system should exist.
